# Soroband design

A macOS menu bar app that meters network usage per network (Wi‑Fi, Ethernet, hotspot) and per app, and keeps every day of history.

Screenshots of the app: [`screenshots/`](screenshots). The UI prototype's screens, which the design was settled on: [popover](mockups/popover.png), [history](mockups/history.png), [history with an app expanded](mockups/history-expanded.png), [settings](mockups/settings.png).

Hotspot Meter keeps a record per network, can start tracking on its own when a hotspot joins, and alerts per session and per network. It meters the interface, so it cannot say which app used the data. That gap is the point of Soroband.

## Decisions

- Distribution: outside the App Store, so no sandbox, and without a paid Apple account, so never notarized. Two routes: a GitHub release's `Soroband.dmg`, signed ad hoc (the first launch needs one Open Anyway), or a build from source on the user's Mac, signed with a certificate made there.
- Menu bar default: today on the current network.
- Data caps and alerts: later, not v1.
- Only internet traffic counts. Flows to local addresses (LAN, link-local, multicast, loopback) are excluded.

## How it works

1. **Network identity.** `NWPathMonitor` reports interface changes and `isExpensive` (set for iPhone Personal Hotspot); the first physical interface of the path (Wi‑Fi, wired, cellular) carries the traffic, after any VPN tunnel. Wi‑Fi is known by its name from CoreWLAN `CWWiFiClient` (needs Location permission), or by its router's hardware address while the name is hidden. When the name becomes readable, the network known by that router becomes the named one: it takes the name's key, keeping its id and history, or, if the named network already exists, its usage is added into it and it leaves the registry. The name is retried each second for 10 s after Location access is granted, because macOS can take seconds to reveal it. Ethernet is known by the router's hardware address, so "Desk Dock" and "Office LAN" stay separate. Until the router of such a network is resolved, its usage is booked to no network ("Unknown network", id 0) rather than to a key two networks would share; the app looks again every second, then every 30 s, until the path changes. The router's address comes from the IPv4 state macOS publishes per network service (`ARPResolvedHardwareAddress` under `State:/Network/Service/<id>/IPv4` in the System Configuration dynamic store): the kernel's ARP table is hidden from apps outside the system on macOS 27. Hotspot = expensive path, or a network the user marks as hotspot. The registry lives in the core's database: each network has a stable id, the key it was identified by, and a name, kind and color the user can change; a known network keeps its edits. Event-driven: nothing polls while an identified network is stable; only a network still waiting for its router (one without IPv4, for example) is looked at again every 30 s.
2. **Per-app counting: our own meter engine.** A small Rust core talks straight to the kernel's network statistics control socket (`com.apple.network.statistics`, protocol in XNU's open source `bsd/net/ntstat.h`). No `nettop`, no private framework. See "Meter engine" below.
3. **Ground truth.** The interface MIB's 64-bit byte counters (`net.link.generic`, `IFDATA_GENERAL`) give the true total per network. `getifaddrs` and the routing socket's `NET_RT_IFLIST2` are not usable: on macOS 27 an unprivileged process gets counters wrapped to 32 bits and rounded to whole kilobytes. Bytes of local-network flows come off it before it is stored (in interface-only mode no flows are read, so they stay in). Flows carry no packet headers, so only a local-network flow's own bytes come off: its headers and acknowledgements, roughly the 8–10% share measured for a bulk transfer (Self-check, below), stay in the network's total. A 100 GB Time Machine backup to a NAS therefore still adds several GB. v0.1 makes no header-byte estimate. Any gap between the stored total and the app sum shows as "Other", local-network headers included.
4. **Storage.** SQLite (system `libsqlite3`, no ORM), WAL mode, `usage.sqlite` in `~/Library/Application Support/Soroband` (Debug builds: `Soroband Debug`). One row per (hour, network, app) with bytes down/up, primary key on those three columns, app names in their own table; the same bytes per (UTC day, network, app) in `usage_day`, written in the same transaction, so History reads whole days from it; interface bytes per (hour, network), less local-network bytes, for the network totals and for Macs on interface totals only. Hours are UTC hour starts. Each poll's new bytes go to the hour the poll ran in, on the network current then; the in-memory bucket is written once a minute, on a network change, at the start of a new day and on quit. Kept forever. Measured with `cargo run --release --example db-growth`: 32–36 bytes a row, 30.9 KB a day (11.3 MB a year) with 40 apps an hour on 2 networks, 12.8 KB a day (4.7 MB a year) with 15 apps an hour on one.
5. **Daily reset.** The menu bar counter covers "today" from a configurable reset hour (default midnight, local time). Nothing is deleted at reset. Today's start is rounded down to a whole UTC hour so it falls on a bucket boundary; in a time zone with a half-hour offset, today starts 30 minutes before the reset hour.
6. **Settings.** The core owns one schema (key, type, default, description) and stores values in `settings.json` next to the database. `soroband config set` validates and saves a value, then posts the Darwin notification `<bundle id>.settings-changed`; the app tells the core to reread the file, so changes apply without a restart.

## Meter engine

**Measured on this Mac** (`prototypes/meter-probe`, 40 s window, 5 s polls, ~150 live connections, a known 20 MB `curl` download):

| Approach | CPU (average) | Memory | Accuracy |
| --- | --- | --- | --- |
| `nettop` streaming (`-L 0`) | 137% (42 s CPU in 31 s) | 4 MB + parsing | n/a |
| `NetworkStatistics.framework` (`prototypes/nstat-probe/nstat-probe.m`) | 0.31% | 7.8 MB | not validated |
| **Own kernel-socket client, Rust** (`prototypes/meter-probe`) | **0.035–0.058%** | **2.0 MB**, 353 KB binary | `curl` 20.03 MB of 20.00; all apps 30.31 MB vs 31.89 MB on the interface (the gap is packet headers, which flows don't carry) |
| **`soroband-core` engine** (M1, `soroband live`, 10 min idle, 5 s polls, 70–95 flows) | **0.017–0.033%** | **1.7–1.8 MB** footprint, 386 KB binary | `curl` 20,032,868 B for a 20,000,000 B body (+0.16%); all apps 8% below the interfaces over 60 s with the download, 22% below on an idle minute |
| The Debug app running the engine (M1, 10 min idle) | 0.023–0.096% | 17.0–23.0 MB footprint | Same engine. Engine cost rises with the Mac's network activity; over the same 2 minutes the Debug app took 0.050%, `soroband live` 0.042% and the M0 app without an engine 0.017% |

How it works:

- One `PF_SYSTEM` control socket. Subscribe to all TCP and UDP flows with a kernel-side filter that accepts only Wi‑Fi, wired and cellular interfaces, so loopback, AWDL and VPN tunnels never reach us. Each flow's own `IS_LOCAL` property drops LAN traffic.
- Every 5 s send one poll; the kernel replies with byte counters plus process name, pid and the effective pid in chunks. Book the delta per flow to (current network, app). Closed flows send a final update, so short connections are not lost.
- **Delegated traffic:** the kernel reports the effective pid when a daemon (`nsurlsessiond`, App Store, `softwareupdated`) or WebKit's networking process moves data for an app, so a background download or a web view's page is credited to the app it serves.
- **Attribution:** a process inside an `.app` bundle is credited to the outermost bundle (helpers, XPC services and login items roll up). Processes under `/System/Library/`, `/System/iOSSupport/`, `/usr/libexec/`, `/usr/sbin/`, `/sbin/` and `/Library/Apple/` (also inside the OS and App cryptexes, and inside an iOS Simulator runtime's `RuntimeRoot`) are "macOS & Services". Any other executable is a command-line tool, named by its file name (`curl`); one installed as `<tool>/versions/<version>`, with a version of dot-separated numbers (`1.4.3`), is named by its `<tool>` directory. A process that exited before it was looked up keeps the name the kernel reported.
- **Retransmissions count.** A flow's received bytes include duplicates from retransmission; they crossed the interface, so they are usage. The kernel reports the duplicates it recognised per flow (`nstat_rxduplicatebytes`), and `soroband live --json` shows them per app as `rx_duplicate`. On a lossy Wi‑Fi a 20 MB download carried up to 568 KB of them (+2.8%). That counter does not cover every re-received byte: on lossy downloads the excess beyond body plus reported duplicates grew from about 33 KB (TLS and HTTP framing on a clean run) to between 59 KB and 234 KB.
- **Exact network switches:** on a path-change event the engine polls immediately and closes the bucket, so bytes land on the network they used, not the next one.
- **Self-check:** the app sum is reconciled against the interface counter all the time (`core/crates/soroband-core/src/check.rs`). Bytes of local-network flows (Time Machine, AirPlay, a NAS) cross the same interfaces, so the check counts them as explained; they are still not usage, so each poll takes them off the interface bytes it stores, and they reach neither a network's total nor "Other / overhead". Their packet headers and acknowledgements are not in any flow, so those stay in both (Ground truth, above). In interface-only mode no flow is read, so local-network bytes stay in the interface bytes. Flows carry no headers, so the app sum runs 8–10% below the interfaces during a bulk download and about 22% below on an idle minute, where headers, acknowledgements and link-local chatter are a large share of small packets. v0.1 makes no header-byte estimate. The rule:
  - The raw gap between the interface bytes and the apps always shows as "Other / overhead" in the popover's Apps tab, with no verdict.
  - The gap is judged over consecutive 10-minute windows, and only in a window with at least 10 MB on the interfaces. Such a window fails when the apps and the local-network bytes together cover less than 85% of what crossed the interfaces.
  - "Degraded" shows after two failing windows in a row, and clears at the next judged window that passes. A window under 10 MB is not judged: it breaks a run of failures but keeps a degraded verdict.
  - The apps and the local-network bytes together summing to more than the interfaces by over 2% flags at once, whatever the volume, because flows never carry more than crossed the wire. The flag stays until a whole window has passed without it.
  - On interface totals only (an unknown descriptor layout) nothing is judged; the popover says per-app counting is off.

Risks and how the design handles them:

- **Layout drift.** The protocol is versioned only by struct size. macOS 27 sends a 360-byte TCP descriptor; the newest published XNU (macOS 26) says 344. The engine reads only stable leading fields (counters, pid, epid, name, interface properties), checks each descriptor's size against a table of sizes observed per macOS version and provider, and falls back to interface-only totals (step 3) when a size is unknown, reporting why. Only macOS 27's kernel TCP and UDP providers are in the table so far (the userland providers sent nothing there); each version added needs a recording from a Mac running it. CI replays the recorded sessions in `core/crates/soroband-core/tests/fixtures`.
- **Idle-flow baseline.** The kernel can skip unchanged flows (`NOZERODELTAS`, `SUPPRESS_BORING_POLL`), but then a flow idle at startup later reports its whole lifetime. Seen in the probe: one Chrome connection added 22.7 MB that never crossed the interface. The engine polls every flow; at ~150 flows this costs 0.058% CPU.
- **Domains.** The kernel has a per-flow domain extension, but it returned nothing to an unprivileged client. Per-domain usage is out unless we add DNS correlation later.

Shape: Rust crate `soroband-core` (socket client, aggregation, SQLite, settings) exposed through a small C API to the app. The app runs as two processes of one binary: the menu bar process (the engine, the network monitor, the menu bar item and the island) runs all day on AppKit alone, and the UI process runs the SwiftUI app and shows every window (see "Two processes" under Performance budget). A network change from the app wakes the engine thread through a pipe, so it polls at once and books what moved so far to the previous network before switching. The same crate gives a `soroband` CLI (`soroband today`, `soroband apps --network Office`, `soroband config`), installed next to the app.

## Resource meter

Each app's CPU time, CPU time billed to it by daemons, disk bytes read and written, energy and memory footprint, beside its internet bytes (`core/crates/soroband-core/src/resources`).

- **Coalitions, not processes.** The kernel groups an app and the processes it starts into a resource coalition, whose counters keep what its processes used after they exit. `proc_listcoalitions` and `coalition_info_resource_usage` read every coalition with no privilege, root apps included, in one call each; they are exported by `libsystem_kernel` but absent from the public SDK, so they are looked up with `dlsym` at launch. Each coalition maps to the app of its processes (`proc_pidinfo`, `PROC_PIDCOALITIONINFO`), named as flows are.
- **Shared coalitions.** A terminal and the commands it runs, or an editor and its tools, share one coalition. Its members outside the leader's app are read with `proc_pid_rusage` and each keeps its own growth; the rest (the leader's own processes, processes that exited, and processes the user cannot read) goes to the members that exited, in proportion to their earlier rate and at most that rate, and what is left to the coalition's leader. A command that starts and exits between two reads is the leader's. On this Mac (a booted iOS Simulator, several agent sessions) a read made about 470 member reads before the leader's own processes were left out and the simulated OS's daemons became services, and about 180 after; a read then took 4–8 ms at the default priority and 13–21 ms at background priority, 70% of it in the coalitions' own reads (about 16 µs each for one with a running process).
- **When it reads.** The system gauges at every engine poll; the resource read once a minute, and at every poll while the CPU is over 50% busy or memory is under pressure, so a burst is seen at poll resolution only when there is one; the volumes once a minute. No thread or timer of its own.
- **Layout guard.** At the first read and hourly, each coalition with at most one exited process (the launcher `xpcproxy`) and only readable members is compared with its members' `proc_pid_rusage` read before and after it. Measured on macOS 27 (894 coalitions, 168 comparable): disk bytes, energy and footprint matched exactly; the coalition's CPU time ran 0–15% below its members' user and system time (median 1%), and billed CPU time up to 53% below on 9 of 168. The guard allows those and judges a field only where no other field's sum would pass for it. A missing call or a failed check moves the meter to the user's own processes (`proc_pid_rusage`), marked on every row it stores.
- **Storage.** Per (hour, app) and per (UTC day, app) in one transaction once a minute; the footprint as a time-weighted sum and its peak. The minute record keeps the gauges, each local volume's free space and the five busiest apps by CPU, footprint and disk written for `resource_minutes_days` days; a minute written twice (the app stopped and started within it) replaces its apps and volumes.

How the app stays inside the budget:

- **Engine:** one socket, one thread blocked in `poll(2)` between 5 s polls. Deltas accumulate in a map keyed by (network, app), about 50 entries. A flow's state is two counters and a name, dropped when the flow closes.
- **Writes:** the in-memory hour bucket flushes to SQLite once a minute, on network change, and on quit.
- **Menu bar label:** an AppKit status item, updated from the engine's poll callback. It redraws only when the displayed text changes, and each redraw costs about 18 ms of the main thread on a Mac with four displays (macOS redraws a copy of the item for each), which at every 5 s poll alone is 0.36% CPU. So a total shows whole megabytes below 1 GB and tenths of a gigabyte above, and a total that only grew redraws at most once a minute; a new network, a layout change or a total that went down at the reset hour redraws at once. A live speed redraws whenever its whole KB/s changes, at most every poll, and is the costly reading; below 1 KB/s it reads "0 KB/s" and does not redraw. One reading without a speed, or such readings inline, are the item's title; anything else is drawn with the icon straight into one bitmap at each redraw (`MenuBarRenderer`, the icon made once per symbol or glyph), the same pixels as `rasterized(itemImage)`, which it drew before, each speed as wide as its widest value ("999 MB/s") so the item does not resize.
- **Two processes:** AppKit and SwiftUI keep tens of megabytes in a process after its first window closes (runtime and framework caches, freed but fragmented heap, kept graphics memory), which no API returns, so no window opens in the process that runs all day. The menu bar process holds the engine, the network monitor and the menu bar item, and runs AppKit alone (`main.swift`): the SwiftUI app lifecycle, with no window, holds about 4 MB in a process from launch (its scene graph and main menu, the symbols of the menu's items, Swift generic metadata, the frameworks' data pages), so only the UI process runs the SwiftUI app. The popover, Settings, History and the Welcome window are in the UI process, a second instance of the same binary started with `--ui` (`app/Soroband/UIProcess.swift`, `UIHost.swift`): one process for all four, so History opened from the popover loads no frameworks again. It starts, with activation prohibited until it shows a window, at the first click; clicks while it launches open the popover once it is ready. Nothing starts it ahead of a click: on macOS 27 MenuBarAgent draws the item, so a tracking area on its button never fires, in the bar or in its overflow, and a global monitor of pointer moves costs the menu bar process about 37 µs for every pointer move anywhere on screen (14% CPU at the 2,300 moves a second `cliclick` makes, 0.058% without it), which no throttle in the handler reduces. The menu bar process quits the UI process 10 minutes after its last window closed (the linger), counting a window as open from the moment it asks for one, so a click never reaches a UI process that has decided to quit; the UI process also quits when its standard input closes (the menu bar process quit). A UI process that died, or that stopped reading (a write to it fails), is replaced by the next request for a window, which is sent again to the new one. The two talk in JSON lines over the UI process's standard input and output: the menu bar process sends a snapshot of what the windows show (the engine's status, today's lists while the popover is open, the registry, the menu bar layout, reset hour and theme, the current network) after each change, so every number is from the same poll as before; the UI process reads the database itself for the popover's past hours and History; every change the user makes (a setting, a network's name or color, the popover's live polls, Quit) goes back to the menu bar process and runs there as before, so the engine's process stays the only writer. The popover is a real `NSPopover` in the UI process, pointing at a transparent, click-through, non-activating panel laid over the menu bar item (as a status item's window is, so the popover draws as key without Soroband in front), which follows the item when it moves; a click on the item toggles it in the UI process, which ignores a click that arrives within 0.3 s of a close, since that click's mouse-down closed it. The menu bar process yields activation to the UI process for every window it asks for. While Settings, History or the Welcome window is open, the UI process is a regular app, so Soroband shows in the Dock and the app switcher; with only the popover open, or none, it is an accessory again. Quit from the Dock or ⌘Q in the UI process asks the menu bar process to quit, so it quits Soroband, not only the windows.
- **Popover:** reads today's in-memory aggregates; from the database it reads the network list (names, kinds and when each was last used) once when it opens, and the hero card's past hours and the History card's days (two History queries, off the main thread) when it opens and at each new hour. The queries also build the apps, networks, heatmap and busiest day that only History shows; on a synthetic year of 200 apps over 31 days of every network, the two reads take 5.7–5.9 ms in all (3.9–4.1 ms in the core, 1.8 ms decoding its 92 KB of JSON), and reading the bars alone would take about 1 ms (Apple M2 Max, Release core). While it is open the engine polls every 1 s for live speed and publishes today's per-app list; when it closes, polls return to 5 s, the list stops, and the popover's view and app icons are released.
- **History window:** in the UI process. After the first popover has shown, it draws a small History offscreen once, so History… does not wait for the first layout of SwiftUI and Charts. Queries aggregate in SQL (`GROUP BY` on the primary keys; whole days from `usage_day`, the hours at the ends of a range from `usage`) on a read-only connection with a 256 KB page cache, run on another thread while the window is built, and return at most a few thousand grouped rows (one per app and network). No stored row loads into memory.
- **Dependencies:** Apple frameworks in the app; `libc`, `rusqlite` (system SQLite) and `serde_json` (the settings file) in the core.
- **App icons:** loaded lazily, small size only, cached by bundle ID.

The spike does none of this (it holds 60 days of fake rows in memory and rescans them every second), which is why it measures 71 MB. It is for the look, not the footprint.

## UI

The popover and History follow the "Warm" direction (`mockups/warm.html`), chosen from three by the user.

**Menu bar item:** an icon and up to four readings in order, each today's total, download or upload in interface bytes (what crossed the interfaces, less the local-network bytes), or the live download or upload speed, counting the current network or every network, in a style (the menu bar layout: `menu_bar_icon`, `menu_bar_readings`, `menu_bar_scope`, `menu_bar_style`). The icon is the network type's SF Symbol, or the Soroband glyph (`app/Soroband/Assets.xcassets/SorobandGlyph.imageset`, the icon pack's template glyph as one path, 14 pt square) on every network. The default is the network icon with today's total on the current network, stacked. Stacked pairs readings in order at 9.5 pt, the first on top, right-aligned; a reading without a partner is drawn at the menu bar's size. Labeled draws each value at 11.5 pt under a 6.5 pt caption (TODAY, DOWN, UP, ↓ LIVE, ↑ LIVE). Inline is one line at the menu bar's size. Speeds read whole KB/s below 1 MB/s, tenths of a MB/s below 10 MB/s. While the engine has stopped it reads "Not counting" beside a warning sign, whichever icon is set.

**Popover** (click the item):
- Hero card, tinted with the current network's color: name, type, when the Mac joined it, live speed, today's total in large type, down/up split, today on all networks, and today's hours as bars from the reset hour (24, or 23 and 25 when clocks change) (hours to come flat, the hour in progress ringed). The past hours are read from the database when the popover opens and at each new hour; the hour in progress is today's live total less the stored hours before it, so it does not trail the total.
- Apps tab: today's top apps on this network, toggle for all networks (bars then split by network color), then "Other / overhead", the raw gap between the interface bytes (local-network bytes taken off) and the apps. A notice above the tabs shows when the self-check is degraded or over-counted, or the engine runs on interface totals.
- Networks tab: today per network; unused ones show "last used".
- Footer: a History card (this month and the last 7 days as small bars on the network History opens on, read from the database when the popover opens; ⌘Y), Settings, Quit.
- Bars grow once when the popover opens; nothing animates after that.

**History window:**
- Sidebar: All Networks, then networks grouped by Wi‑Fi / Hotspot / Ethernet, each icon in its network color; "Connected" badge on the current one.
- Toolbar: Day / Week / Month / Year / All Time, previous/next, Today, Export CSV (every stored (hour, network, app) row of the range and network shown). Opens on this month: on the current network when the popover's Apps tab shows only that network, on every network otherwise.
- Headline card: the total in large type with its change vs the same elapsed span of the previous period; download, upload, daily average and busiest day; a download/upload ratio bar. Beside it on All Networks or with more than one network, Where it went: one 100% bar plus a row per network with share and bytes.
- Usage chart, full width, its legend and average in the header: bars stacked by network (one color for a single network) of what crossed the interfaces less the local-network bytes: hours for Day, local days for Week and Month, months for Year, days or months for All Time (months past three months of history); dashed average line over the bars elapsed so far; the busiest day and today labelled above their bars; hover tooltip listing each network and the total for that bar.
- Apps: the top 12 apps (Show all for the rest) with their share of the total and a bar split by network, then "Other / overhead"; click an app for its download/upload per network.
- When you use data, beside the apps: weekday × hour heatmap (Week and longer), hover a cell for its value, and one sentence naming the busiest hour and the share of usage between midnight and 7:00. Local days, hours and weekdays come from each stored hour's middle, so in a half-hour time zone an hour belongs where most of it falls.
- Shows what has been written: up to a minute behind the popover.

**Dynamic Island moments** (optional, see [mockup](mockups/island-moments.png)):
- The menu bar item is always present and is the main element; the island never replaces it.
- One black shape hanging from the top edge: at rest it is exactly the notch (nothing on a display without one); a glance widens it sideways; a moment grows it into a panel, and content fades in after the shape has grown (0.14 s later, over 0.22 s, from 96% scale at the top).
- Style setting: **Seamless** (default) covers the menu bar next to the notch while a moment is open, like other notch apps. **Keep menu bar clear** keeps the shape notch-wide inside the menu bar and widens it only below, so no menu bar item is ever covered.
- Moments, each switchable in Settings:
  - **Peek on hover:** rest the pointer on the notch for 0.4 s: today on this network, live speed and the top 3 apps, following each poll while open.
  - **Network joined:** this network's usage over the last 7 days, the last hour it was used before, today here. Not for the network the Mac is on when Soroband starts.
  - **Network left:** session receipt: what crossed the network's interfaces since the Mac joined it, how long, the top app.
  - **Hotspot meter:** a glance while on a hotspot: today on it beside the hotspot symbol on the left of the notch, the live speed on the right (seamless), or a small band below the notch (keep menu bar clear).
  - **Data hog:** one app over a threshold within a window (default 100 MB in 5 min). Actions: Pause until off hotspot (on a hotspot, when the setting allows it: quits the app and opens it again, in the background, on the next network that is not a hotspot), Ignore app, Details (History on today, with the app expanded).
  - **Background activity:** an app over a threshold within the same window (default 50 MB) counting only the bytes it moved while it was not the frontmost app. Actions: Details, Ignore app. An app over both thresholds in one burst is one alert, the data hog.
  - **Large transfer:** an app moving at least 100 KB/s poll after poll, shown once the run passes a threshold (default 50 MB) with its bytes and speed, and again with a checkmark once the app has moved less than 100 KB/s for two polls. A transfer a system service makes for an app names it ("Xcode via App Store"; the App Store and Software Update are named).
  - **Daily recap:** one line at the reset hour: the day that ended on every network, how many networks, the top app. Off by default.
- One moment opens at a time; the others wait in the moment queue, alerts (data hog, background activity) first, then large transfers, then the rest, at most 8. A moment closes on its own (alerts after 8 s, a transfer after 6 s, the peek 0.4 s after the pointer leaves, the others after 5 s) and the next opens 0.45 s later. The pointer on the island's outline keeps a moment open; a pointer resting where a moment opened counts only once it moves, so a moment that opens under it still closes. A click on the island outside its buttons closes the open moment and drops the waiting ones, also between two moments; a dropped transfer counts as shown, so only its end opens it again. A click on the peek, or in the gap after it, closes only the peek, since the moments waiting behind it have not been seen. A transfer is one moment per app: its progress updates it, and once it has shown, only its end opens it again.
- Hover and clicks are tested against the island's outline, not its panel; the panel tracks the pointer only over the outline's bounds.
- Full screen: an app in front with a window covering a display the island is on. By default only alerts show then; the island can hide entirely or show every moment.
- Displays: the built-in display (default) or every display; on a display without a notch the island grows from the top edge, or, keeping the menu bar clear, from just below the menu bar.
- Island off, or on with no display to show on (the built-in display only, with the lid closed): alerts become notifications (`island_notifications`, on by default; macOS asks for permission once).
- Apps can be ignored: they raise no moment (`island_ignored_apps`).

How the island is built and what it costs:
- **In the menu bar process, in AppKit and Core Animation** (decided 2026-11-05, measured in `prototypes/island-spike`). The SwiftUI prototype's look is reproduced: the same outline, the same spring (response 0.45 s, damping 0.8, stepped per frame by a display link), the same content transition. Screenshots of the two renderers differ in under 0.15% of pixels, and recordings of the opening match frame by frame from the third frame on. An AppKit agent with a status item grew 3.8–4.3 MB after 30 moments with the AppKit island, 5.5–5.7 MB with the SwiftUI one; both rested at 0.001% CPU, and a moment cost about 50 ms of CPU in AppKit against 200 ms in SwiftUI. The UI process was the other place considered: it would have to run all day with the island on (42–57 MB more) or start for each moment (0.5–0.8 s late).
- **The engine finds the traffic moments** (`core/crates/soroband-core/src/moments.rs`): it watches each poll's bytes per app only while the island or its notifications are on, and hands the app what it found (`soroband_moments_json`) after the poll; the frontmost app comes from `NSWorkspace` activations. The joined and left moments come from the engine at a network change, the recap at the day's end.
- **Nothing runs while nothing shows:** one transparent panel per display, a display link only while the shape moves, one timer to the queue's next change, and no work at a poll beyond taking the engine's list (an empty `[]` most of the time) unless the peek or the hotspot meter is open.

**Settings:**
- A window with a sidebar (General, Appearance, Menu Bar, Island, Networks, About), each page a large title over grouped cards.
- General: when a new day starts (the reset hour, with a ruler marking the hours that count toward the day before), open at login, Location access for Wi‑Fi names, and where the data is (Show in Finder).
- Appearance: the theme of Soroband's windows. Appearance is three cards, System, Light and Dark, each sketching a window in it (`appearance`); the accent color is a row of labeled swatches, System first, then the eight colors of Soroband's icon pack (`accent`). Both default to System and apply at once. App Icon is a grid of Soroband's 13 icons, five to a row, each labeled, the pick ringed (`app_icon`, default Graphite), each drawn once into a 48 pt bitmap rather than shown from its `.icns`.
- Menu Bar: a preview of the menu bar pinned above the page, drawing the item with the same image the menu bar uses (today's numbers, or sample ones before the first count), its width, and a warning past 160 pt, where it may be hidden beside a MacBook's notch. Readings are tiles to check, up to four, in two groups (today, live speed) with what each reads now; the order tray groups them as the style draws them and moves one by dragging it onto another, or by its context menu; three style cards each draw the item in their style; "Count today on" picks the scope. Every change applies at once; Revert Changes goes back to the layout the page opened with, Restore Default to today's total.
- Island: master switch (off means a plain menu bar app), style (seamless or keep menu bar clear), or "send alerts as notifications" while the island is off; each moment on/off, thresholds for data hog, background activity and large transfer; full-screen behavior, the pause action, built-in or all displays; the ignored apps, each with Remove.
- Networks: each known network with its color (click it to pick one of the five slots, or Automatic for its place's), rename in place, kind, and whether it is connected or when it was last used.
- About: the app icon, and the version with its build number and build stamp (`Version 0.1.0 (412) · 16e85ce main`), as `soroband version` prints them.
- Data: export CSV, show database.

## Visual language

- Networks use categorical slots in fixed order unless the user picks one (`networks.color`, schema version 3): blue, orange, aqua, yellow, magenta (light and dark steps differ, `prototypes/ui-spike/Sources/Soroband/Model.swift`). Validated with the dataviz palette checker: all checks pass in dark mode; in light mode aqua, yellow and magenta sit below 3:1 contrast, so every colored mark has a text label next to it. A network keeps its color in every view.
- Magnitude (heatmap) uses one blue ramp whose low end fades into the background.
- The app icon (`app/Soroband/AppIcon.swift`): Graphite is the bundle's own icon (the asset catalog's `AppIcon`); the other 12 are `.icns` files built from Soroband's icon pack with `iconutil` (`app/Soroband/AppIcons/`, about 13.6 MB of the bundle), every size from 16 to 1024 pixels, so small sizes are drawn, not scaled. macOS draws the bundle's icon on its grid (824 of 1024 pixels, with a shadow) but a custom icon as it is, so the others are drawn on that grid too, or they would stand larger than Graphite and every other app. The UI process sets `NSApp.applicationIconImage` (the Dock while a window is open, and About; nil for Graphite). The menu bar process keeps Finder's icon: when the setting changes, and at a launch only when the bundle lost it (an update replaced the bundle) or holds another one, it starts its own executable with `--write-finder-icon`, which calls `NSWorkspace.setIcon` (an `Icon\r` file in the bundle's root) and exits; the same call in the menu bar process kept about 23 MB there after one write. A launch reads only whether `Icon\r` exists, whether the bundle is writable and the icon it last wrote (`UserDefaults`). Graphite takes the custom icon off again. A bundle this account cannot change is never written; Settings says Finder keeps the default. Debug builds write it only with `SOROBAND_FINDER_ICON=1` (`docs/verification.md`). The `Icon\r` file is outside the signature's seal, so `codesign --verify --strict` fails on the bundle while it is there; `soroband update` and `scripts/install.sh` replace the whole bundle without checking the installed one's signature, and the next launch writes the icon again.
- The theme (`app/Soroband/Theme.swift`) applies to the UI process's windows only: the popover, Settings, History and the Welcome window. Its appearance sets `NSApp.appearance` there (nil for System) and the popover's own `appearance`, which the popover does not take from the app; the island, drawn by the menu bar process, stays dark. Its accent is the SwiftUI tint at each window's root (`themed()`), and what Soroband draws to show a selection or highlight uses the `.tint` style, not `Color.accentColor`, which does not follow a tint; controls macOS draws itself (segmented controls, the sidebar's selection, focus rings) may keep macOS's accent color. Each accent has a light and a dark step taken from its icon's gradient in Soroband's icon pack, at least 3:1 against the light window (#ECECEC) and the dark one (#1E1E1E), with a white glyph on each step at 3:1 or more too (a selected reading's tile), as `ThemeTests` checks; network colors and the heatmap's blue are data colors and do not follow the accent.
- Apps are not colored; their bars carry network colors.
- 2 pt gaps between stacked segments, 2 pt corner radius, recessive grid.

## Prototypes

Throwaway code that settled the design; the product code lives in `app/` and `core/`.

- `prototypes/meter-probe`: the engine prototype. `cargo run --release -- 40 5` prints per-app internet bytes for 40 s (`METER_DEBUG=1` for message diagnostics).
- `prototypes/nstat-probe`: the same measurement through `NetworkStatistics.framework`, kept for comparison.
- `prototypes/island-spike`: the island in an AppKit agent with a status item, drawn with Core Animation or with the ui-spike's SwiftUI view, measured over 30 moments (`run.sh`) and filmed for a frame-by-frame comparison (`--record`). It settled where the island runs (Dynamic Island moments, above).
- `prototypes/ui-spike`: SwiftUI app with 60 days of fake data and fake live traffic. `run.sh` launches it in the menu bar; `snapshot.sh` re-renders `docs/mockups/`. The ⇅ button in the popover simulates joining another network (which fires the left and joined moments) and fires any moment on demand. `SOROBAND_DEMO=dataHog .build/debug/Soroband` fires one moment at launch.
- `prototypes/sysmon-probe`: CPU, memory and disk monitoring. `bench` times one call of each source; `run <idle|gauges|scan|coal|tiered> <secs>` polls every 5 s and prints its own CPU and footprint; `top` and `energy` compare each coalition's CPU, footprint and energy with the sum over its processes. `run.sh` repeats the 10-minute comparison under the measurement lock.
